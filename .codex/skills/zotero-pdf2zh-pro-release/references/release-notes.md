# Release 写作规范

读者需要知道为什么值得升级、是否影响自己、需要做什么。使用中文，产品名、文件名和命令保留原文。正文默认一屏可读，以便快速扫读为目标；必要的升级要求和仍适用的重要限制不受篇幅限制。

## 默认布局

- 顺序为：一句话概括 → 3–4 条重点 → 必要的升级提醒 → 底部链接。短补丁可省概括、只列 1–2 条，不凑数量；没有额外操作要求时省略提醒。
- 用留白和少量加粗区分层次，条目采用“**简短主题**：一句说明”。短日志无需再加“新增”“优化”“修复”等分类标题，不堆 emoji、徽章、表格或嵌套列表。
- 升级提醒集中放在变化之后；存在破坏性变化或必须先完成的操作时置顶，并写明受影响版本。不要在开头、条目和结尾重复同一要求。
- 底部用简短链接文字，以 ` · ` 分隔安装入口、安装指南和完整变更；按需保留，不逐项列出所有附件。正文过长时先筛选、合并内容，确有必要才分组，不靠折叠块塞入次要细节。

## 内容取舍

- 核对全部改动是为了准确筛选，不代表全部写进 Release。优先写本版最重要的体验变化、影响使用的修复和需要用户行动的事项，按用户影响排序。
- 每条只表达一个主要结果，通常一句即可。例如“修复含大量散点图的论文解析缓慢”，比“添加字体 cache、更新模块”更有用；合并同一功能的多个实现提交，不用分号把多个主题挤成一段。
- 只写有证据的性能数字和兼容范围，避免“全面提升”“大幅优化”等缺少具体结果的表述。
- 研发细节、测试数量、CI 重试、构建缓存告警、提交过程通常不属于公开正文。依赖版本、缓存布局、日志轮转等只有影响用户操作时才展开；其余通过完整变更追溯。
- 不写完整 commit SHA、逐附件 SHA-256、机器校验清单或很长的原始 git log；也不把它们藏进折叠块。需要追溯时用 tag、PR/issue 或“完整变更”链接。
- 完整 SHA 保留在 tag、Actions 制品身份、`checksums.json`、自动更新清单和 Homebrew revision 中。不要修改校验逻辑来缩短文案。
- 文案与机器输出分开：`CHANGELOG.md` 对应段落是发布正文来源；本地脚本和 PyPI workflow 都不得自动追加哈希表。
- GitHub 自带的 tag/短提交显示或资产 digest 不属于手写正文，无需设法移除。

## 安装与升级说明

只写本次必要的操作和限制，常规教程链接至对应 tag 的 `docs/user-guide.md` 或 README；下列事实用于按需取舍，不是每版都要复制的安装清单：

- Zotero 用户安装 XPI 或检查插件更新；服务端需单独更新，不能暗示插件更新会同时升级 Python 服务。
- Windows 用户下载单 EXE 安装器并按向导安装或升级；首次准备 Python 与翻译依赖需要联网，ZIP 用于自动更新。涉及安装方式变化时再说明这些区别，不每版重复控制中心框架或 WebView2 等背景。需等待翻译完成、停止旧服务或手动恢复时，明确受影响版本、操作顺序及配置和任务数据是否保留；历史版本说明保持当时的安装方式。
- macOS 的 Homebrew 更新与服务重启命令以当前 README 为准。只有处理明确的本机 pin 问题时才讨论解除 pin，不把开发机状态变成所有用户的操作要求。
- 同版本客户端修订需解释哪些包变了、PyPI 是否保持原包、已安装同版本用户如何手动覆盖，以及数据是否保留；不使用源码 SHA 对作为用户说明。
- 已知限制须绑定具体版本和证据，不能把 v1.6.9 的历史限制复制到新版本；也不能为了简洁删掉仍适用的重要限制。

## 示例结构

下面仅示范写法；条目、升级要求和链接须由本次真实变更生成，不能把示例当作已验证结果，也不要固定套用其中的提醒。

```markdown
## vX.Y.Z - YYYY-MM-DD

本次更新改善复杂 PDF 的解析与任务诊断体验。

- **解析修复**：解决含大量重复散点图的论文解析缓慢的问题。
- **任务管理**：改善卡住任务的终止流程。
- **问题反馈**：支持导出脱敏诊断包，便于排查翻译问题。

**升级提醒**

插件与本地服务需分别升级；更新插件不会自动升级服务。

[Windows 安装器](https://github.com/study-233/zotero-pdf2zh-pro/releases/download/vX.Y.Z/zotero-pdf2zh-pro-windows-x64-setup.exe) · [安装指南](https://github.com/study-233/zotero-pdf2zh-pro/blob/vX.Y.Z/docs/user-guide.md) · [完整变更](https://github.com/study-233/zotero-pdf2zh-pro/compare/vPREVIOUS...vX.Y.Z)
```

检查草稿时，先看能否迅速找到本版重点和自己需要执行的操作；超出一屏时优先删减次要细节，不删关键提醒。确认下载链接对应本次实际制品，compare 使用前一实际已发布 tag，不简单将补丁号减一。仅文案修改不重新打 tag、重建、重传制品；只有用户要求修改线上正文时才执行 `gh release edit ... --notes-file ...`，并读取确认保存结果。

## 参考的开源实践

2026-09-29 阅读以下官方页面，取适合本项目的部分，并非照搬全部格式：

- [Zotero Version History](https://www.zotero.org/support/changelog)：短条目描述具体行为和受影响平台，开发者变化单列。
- [uv 0.8.22](https://github.com/astral-sh/uv/releases/tag/0.8.22)：变化、安装和下载分开，下载表的校验值通过链接提供，不用长串哈希占据正文。
- [OBS Studio 32.0.4](https://github.com/obsproject/obs-studio/releases/tag/32.0.4)：热修复放前面，按新增、变化、修复分组。它也包含哈希块，本项目遵循用户偏好不采用该部分。
