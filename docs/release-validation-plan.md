## 更新系统的维护边界

当前 [更新器](../windows-app/src/update.rs)下载完整 ZIP，校验大小、SHA-256、地址和包版本；
[安装脚本](../scripts/windows/install.ps1)依据锁定依赖及 wheel 身份准备独立运行环境；
[事务实现](../scripts/windows/runtime.ps1)保留旧运行环境，切换后检查健康状态，失败则恢复。
这些基础值得保留，优先完善契约和验收，不需要重写更新器。

将以下三个维度分开维护：

1. **应用版本**：每次发布改变，例如 v1.9.1 → v1.9.2。
2. **安装和更新协议**：目录布局、环境指针、维护接口、清单格式、客户端交接约定。只有这些约定变化才增加兼容分组。
3. **数据格式**：任务、配置、词表、SQLite 等各自的 schema 或 migration 标识；没有结构变化时不随应用版本递增。

项目已有任务文件 `schemaVersion=1` 和 SQLite 按列补充逻辑。应从现有格式扩展，
下一次真正需要结构迁移时再加入有序迁移记录，不为此次补丁一次性新建庞大的迁移框架。

应用可从旧版直接换成最新完整包；数据如有需要可内部执行 S1 → S2 → S3，
不要求用户安装包含这些迁移的每个应用版本。需验证重复运行、已有部分迁移、中断与坏数据的处理。

**运行环境回滚不能自动等同于数据回滚。** 当前事务主要备份 bin 文件、版本标记和运行环境指针，
并没有对所有用户数据建立版本快照。未来不兼容的数据迁移必须先决定旧程序可读性、备份及恢复方式；
对 SQLite 应使用一致性备份或停写后的复制。不能在回滚时覆盖升级后用户产生的新任务。

更新协议变更还必须考虑旧客户端。当前清单读取器只接受 `schemaVersion=1`，也没有最低客户端能力字段。
单纯给最新清单新增 `minVersion` 不能让已安装的旧程序自动遵守新规则。
应优先维持旧协议；确实无法兼容时，先交付能识别新规则的桥接版本，或保留旧 feed 并提供明确的手动安装路径。
协议 reader、清单 writer、安装入口和旧版本验收必须一起验证。

## 建议的自动验证矩阵

“上一版本”指小于候选版、具有所需制品的最新正式发布，排除 draft、prerelease 和本次候选。
发布开始时解析一次，冻结 tag、提交、附件摘要和 wheel 摘要到记录中；恢复过程中不重新选择浮动 latest。
下载失败应记录未完成，不能悄悄换个旧版本或跳过。

| 层级 | 执行时机 | 必须证明的行为 |
| --- | --- | --- |
| 快速契约与单测 | 每次相关提交/PR | 平台测试确实在对应平台执行；发布状态、内容冲突、版本解析、清单兼容、事务与失败清理正确。 |
| 最终制品基线 | 每次正式发布 | 延续现有最终包、全新安装、运行时/OCR、启动、进度、哈希和渠道可用性检查。 |
| 上一正式版真实升级 | 每次正式发布，复用同一次构建 | 真实旧 GUI/wheel → 本次最终 GUI/wheel；版本确实变化，用户数据和设置可读，服务正确交接。 |
| 当前布局最早支持版本 | 更新链路、安装布局或打包依赖变化；另作周期回归 | 跨多个补丁直接升级。与上一正式版相同则去重。v1.9.0 可作为待确认基线，不能只因版本号推定已验收。 |
| 历史布局代表 | 涉及旧布局、进程归属、维护接口、迁移路径的变化；另作周期回归 | v1.8.2 代表旧 uv tool 布局。修好夹具后真实运行，验证停服务要求、原数据保留及新程序接管。 |
| 支持的数据格式快照 | 相关持久化/迁移代码变化；廉价部分进入核心 CI | 每种受支持 schema 的小型合成数据都能迁移并被新版读取；重复执行、中断、损坏和回滚策略可测。 |
| 分发平台专项 | CLI、依赖、打包、启动方式变化 | 对应 uv/PyPI、Docker、Homebrew 的实际安装和启动；Ruby audit 不等于 brew install。 |

周期回归建议先采用每周一次，只跑少数兼容代表，验证当前代码或既有候选制品。
已加入 `windows-compatibility.yml`，默认分支收到该工作流后生效；本轮未推送或触发线上任务。
周期失败必须自动建成可见的失败状态；已有证据显示支持路径被产品破坏时，后续发布不能借“不是本次变更”绕过。
网络不可用、夹具准备失败与产品升级失败应分开记录，均不能记为通过。

普通补丁保留一条上一正式版 → 候选版的真实升级，加全新安装与快速契约测试。
本次 v1.9.2 同时修改任务管理、维护接口和翻译缓存，由风险规则自动追加扩展验证。
不需要再把 v1.4、v1.5、v1.6 等逐个安装一遍。安装/数据/更新协议变化时，追加相应代表性旧基线。
仅有 A → B、B → C 通过也不能证明 A → C 直接升级，所以要保留最早支持版本和历史布局的跨越测试。

近期升级测试应调用旧版真实交接入口与新版最终载荷。准备/安装阶段可注入已验明的本地制品，
清单解析、下载校验和交接另做协议契约测试，避免将“调用新版安装脚本成功”扩大解释为旧客户端更新全过程已通过。
数据检查必须读取真实格式的测试任务、配置及词表；仅断言一个 `preserve-me` 文件存在不够。

## 实施顺序与验收条件

### 第一批：发布保护与证据正确性

范围：F03、F04、F05、F06、F07。优先修改现有入口和守卫，避免同时重构整个发布系统。

- 普通恢复：附件不存在才补传；同名且摘要相同则复用；不同则停止。默认不使用 `--clobber`。
- `--no-pypi` 只跳过上传。凡将公开分发依赖 PyPI 的安装器，都必须确认对应 wheel/sdist 完整且匹配。
- 分别表示产品源提交、工作流提交、测试脚本提交和 run ID/attempt。工作流提交的祖先关系只是条件之一，还需验证制品清单来源和内容摘要。
- dispatch 使用唯一关联标识并持久化准确 run ID；查询不得只凭产品 SHA 或“时间窗口里第一个 run”。
- 覆盖/恢复共用一份文件集合。失败也执行恢复；测试从真实覆盖步骤派生集合，不能再复制一份遗漏清单。
- 标准与完整成功分支均生成正确报告。退出码、必需场景结果和最终状态必须一致。

验收：自动测试覆盖“附件缺失/相同/冲突”、跳过上传但包缺失/冲突、工作流为产品后代、并发 dispatch 不串 run、
策略中全部覆盖文件均恢复（修复后为 15 个）、标准成功和失败报告。所有守卫测试均用离线桩或临时仓库，不向正式渠道写入。

### 第二批：补齐真实升级与测试调度

范围：F01、F02、F08、F09、F10。

- 单独保留同版本重装测试，新增参数化的近期跨版本升级场景；历史 v1.8.2 保留为独立场景。
- 旧版夹具重建私有 uv、工具目录、环境变量和可重现依赖约束；先证明旧服务正常启动，再测试迁移。
- 旧基线制品和测试约束集中记录来源与摘要，缓存按内容寻址；不能依赖当天解析出的最新依赖修复旧环境。
- 在现有 Windows job 执行 Windows 开发管理测试，不增加原生 GUI 编译。
- 进度测试由调用者提供 EXE、uv、Python，记录版本和摘要；发布模式缺少必要输入必须失败或标为未完成。
- Slint 历史专项若继续使用，接受明确的候选版本并核对安装器；原手工 UI 结果仍需明确标为已执行或待执行。
- 增加小型测试目录：记录场景 ID、平台、必需输入、所属层级和入口。与实际发现的测试/CI 调度对照，检查无调用入口和意外 skip。

验收：真实旧版升级后服务版本变化、数据可读、原设置保留、旧进程退出；历史基线与近期升级分别报告。
在干净 runner 删除开发缓存后，必需场景不能显示“全 skip 但发布通过”。
夹具失败要能定位为 baseline setup，不能误称目标迁移失败。

### 第三批：自动选测与断点恢复

范围：F11、F12，以及让前两批修复持续有效的机制。

保留 `release.sh` 作为入口，把散落的状态协调逐步提取为一个小型 Python 模块，
让本地发布和 Actions 使用相同的规则。不要建立第二套平行发布实现。

由 `scripts/release-policy.json` 集中维护兼容分组、基线选择、场景分层和高风险文件范围。
版本、附件及入口信息优先从现有构建元数据读取。
测试目录可以放在同一配置中，避免再维护一份相同清单。

选测依据是“最后发布产品提交 → 本次产品提交”的实际差异，包含升级器、安装脚本、服务维护接口、
持久化代码、打包工具、依赖锁、CLI 和发布清单生成器。依赖变化也可能影响旧版升级，不能只按文件名含 update 判断。
未知类别保守追加检查；人工选项可以扩大验证范围。调整兼容政策需要可审阅的配置变更和理由。
输出计划必须显示选中场景、排除理由和基线身份，给发布程序直接使用，不再让维护者手工解释。

发布记录至少包含：

| 类别 | 字段含义 |
| --- | --- |
| 身份 | 候选版本、产品源提交、工作流提交、测试脚本摘要、策略版本、关联标识。 |
| 制品 | 构建 run ID/attempt、各制品的大小和摘要、被冻结的旧基线。 |
| 场景 | 场景 ID、验证环境/工具版本、所用制品、通过/失败/未完成/不适用、证据位置。 |
| 发布阶段 | 核心检查、构建、制品验证、PyPI 可见、Release 附件、更新入口、Homebrew。 |

每个阶段幂等：先核验已完成的远端事实，再决定是否执行；本地断网时标为待重新观察，不能认定远端构建失败。
观察与下载设置有限超时、有限重试和无进展上限；失败后保留 run ID，恢复时先查询既有 run，不重新 dispatch。
重试更新前先校验远端 tag/附件身份，避免恢复到另一批制品。

证据复用条件至少是相同制品摘要、相同基线、相同场景契约及兼容的验证环境；仅产品版本相同不够。
测试脚本改动只重跑受影响场景；产品或构建输入改变才重建。跨平台渠道不能冒用 Windows 通过结果。
活动中的发布记录须保留，避免被 30 天报告清理规则清掉；发布完成后把最终清单和验收记录归档到持久构建记录。
兼容基线制品不能只依赖 Actions 的短期 artifact 保留期。

验收：在构建完成、下载中断、PyPI 完成、附件部分上传等位置注入故障，恢复后只补缺失阶段；
重复运行不会重建、重复发布或覆盖冲突内容。测试、产物集合与文档中的机器事实由同一配置生成或检查。
skill 只保留执行入口、授权边界和规范链接，不继续复制易漂移的版本、路径与场景列表。

### 第四批：下一次兼容边界变化前完善数据迁移

范围：后续结构演进，不作为本次纯补丁必须完成的大重构。

- 在实际结构变化时增加明确 migration，保留各支持格式的最小合成快照，不保存用户真实凭据或任务。
- 验证最早支持 schema 到当前、重复执行、部分完成、异常中断、恢复及旧程序可读性。
- 只有安装/协议/数据契约变化时才新增兼容分组；普通补丁只更新当前产品元数据，近期基线自动推进。
- 取消旧布局支持时，明确更新提示和保留数据的手动路径，经过兼容决策后再退役对应测试。

## 对当前 v1.9.2 的建议

v1.9.1 到候选产品提交的 Windows 安装/更新逻辑没有实质变化，相关文件差异为版本标记。
但持久化和维护代码存在实质变动，自动策略会为本次候选追加扩展检查；不能只看 Windows 安装脚本判断风险。
这不意味着今后每个补丁都必须重复 v1.8.2 全链路迁移。
但已发现的夹具问题必须修复并取得一次可靠基线，不能长期留在“需要时再手工处理”的状态。

先落地第一批保护和第二批必要验收，再复用已有候选制品完成近期真实升级。
是否复用必须由清单和摘要确认；修复阶段已重新查询原构建制品，确认仍可下载，再进行有界下载。
纯测试/工作流修复不要求重编译；如果最终修改了打包或产品输入，则重新构建受影响制品。

最终完成标准：维护者运行一次发布入口，即得到有明确基线和理由的测试计划、可靠验收结果、可恢复阶段记录；
普通补丁不需要人工枚举旧版本，不需要手动检查每个脚本是否仍指向旧程序，也不需要凭聊天记录续接发布。
