# Actions 测试规范

[开发维护笔记](development-notes.md#测试)

问题复核、设计依据和实施记录见[发布与更新验证改进计划](release-validation-plan.md)。
选测规则与兼容基线统一维护在 [release-policy.json](../scripts/release-policy.json)。

测试按风险与运行环境安排。Windows 开发优先利用本机工具链和缓存；macOS 开发或
本机缺少 Windows 验证条件时，由 Actions 执行必要的 Windows 检查。Windows 正式发布
优先在本机构建并验收最终制品，再由轻量 Actions 任务核验和归档；同一批制品的成功检查直接复用。

## 日常提交与 PR

| 检查 | 内容 | 执行位置 |
| --- | --- | --- |
| 核心 CI | 插件构建、lint、单测；服务端及发布守卫 | Ubuntu Actions，最多 15 分钟 |
| Windows 快速检查 | PowerShell 5.1 语法、路径和进程归属、开发管理、快捷方式、事务回滚、清理、进度、卸载及发布守卫 | Windows Actions，最多 10 分钟 |
| Codex 原生兼容 | 发现、启动和进程清理；不依赖真实账户 | Windows / macOS Actions，每个平台最多 10 分钟 |
| 文档与官网 | 本地链接、版本一致性、文档测试与网站构建 | 合并工作流，验证最多 10 分钟 |
| 安全检查 | Python、JS/TS、Actions 的 CodeQL；PR 新增依赖漏洞 | Security，CodeQL 每种语言最多 20 分钟 |

- 每次相关提交保留远端 Windows 快速检查，不能因开发机是 Windows 就关闭。
- 日常 CI 不下载 LLVM/Skia，不编译整套原生 GUI，不安装完整翻译环境，不调用付费 API。
- 原生代码有改动时，Windows 本机先跑受影响的 Rust/脚本测试；Mac 上可按需触发
  `build-windows-release.yml`，使用准确提交。在正式发布前必须取得原生构建证据。
- 同一分支的新 CI 取消尚未结束的旧 CI；发布工作流不自动取消，避免中断分发。

## 正式发布

1. 最终发布提交通过核心 CI。修复产品源码或打包输入后，应重新取得受影响的证据。
2. Windows 本机对该提交构建一批正式制品；工具链不足或显式指定时使用 Actions。Rust 单测复用同一次 release 编译的依赖；
   不另外编译 debug 或在不同 job 重建同一安装包。
3. 对最终制品保留必要检查：版本与来源、PE/DLL、安装器载荷和大小、启动窗口、
   全新 Python 3.13/OCR、隔离安装与自更新、进度输出及自动更新清单；另用上一正式版
   的真实 GUI/wheel 升级到最终包，读取既有任务、词表、翻译缓存和设置。
4. 按变更范围追加场景，见下表。所选生命周期在实际构建主机对最终制品执行一次；
   Windows 本地模式执行全部选中场景，远端构建模式的本机只补显式兼容升级。Mac 或本机条件
   不足时，历史升级也由远端 Windows 执行。
5. 发布阶段复用该提交已通过的插件、服务端及轻量脚本测试。`full_validation`
   表示额外 Windows 场景，不表示重复所有平台的全量测试。
6. 所有必需验证完成后，才发布 PyPI、GitHub Release 与 Homebrew。官网和用户更新
  说明不堆放测试日志；内部记录保留提交、run、制品哈希、验证环境和结果。

统一入口为 `bash scripts/release.sh <version>`，`--build-source auto` 默认选择可用的 Windows
本地工具链，`--build-source local` 强制本机，`--build-source actions` 显式使用远端。
本地模式复用既有 LLVM/Skia 和 release target，可通过 `LLVM_HOME`、`SKIA_SOURCE_DIR`、
`CARGO_TARGET_DIR` 指定已准备的工具链与缓存。构建、原生测试、打包和各验收阶段分别记录，
测试失败后恢复不会重做已验证的构建；产品、工具链、计划或制品变化使相应记录失效。
本地产物连同 Windows 环境、阶段结果、冻结计划和八项文件摘要上传至候选草稿附件，轻量 Actions
核验全部摘要、包内容、源码身份、核心 CI 和验证契约后归档，后续沿用该 run 的原包和 PyPI OIDC。
候选草稿不进入正式更新渠道。原生测试默认最多两个并发线程，避免大量 PowerShell 探针争用。
入口按上一正式版到候选的实际差异
自动选择安装、依赖和持久化场景；仅本项目版本标记变化不扩大范围。

| 变更范围 | 生命周期 | 历史升级 |
| --- | --- | --- |
| 已分类的普通改动、插件、文档、Docker 配置 | 标准安装、覆盖安装、自更新及清理 | 上一正式版 |
| 服务端数据格式、持久化模块或依赖 | 标准流程，数据格式由合成夹具补充回归 | 上一正式版 |
| Windows 安装、启动、更新、目录布局或安装器 | 标准流程加故障恢复、保留数据卸载、重装、迁移目录及回滚 | 上一正式版 |
| 未分类路径、显式完整验证 | 完整生命周期 | 上一正式版 |
| 定期兼容回归 | 完整生命周期 | 最近三个版本窗口内，最多两个旧版到最新正式版 |
| 显式历史调查 | 所选生命周期 | `--baseline <version>` 明确指定；不自动追加旧布局 |

具体文件归属以策略的 `riskGroups` 为准；多个范围取并集，同一基线去重。
`knownPaths` 不再用 `server/*` 兜底，新服务端模块必须分类，否则保守完整验证。
`--full-validation` 扩大生命周期场景，不扩大历史版本范围；自动选测只开启所需场景，不把数据改动升级为
完整生命周期。Windows 默认本地补历史升级；加 `--remote-validation` 可改为全部远端执行。
同版本替换沿用独立的远端完整验证与备份要求。

上一正式版排除草稿、预发布及本次候选；最新稳定版缺少必需附件时停止，不回退到更旧版本。
发布开始时冻结基线提交、GitHub 附件及 PyPI wheel 摘要；旧 uv tool 基线使用原 tag 的
`uv.lock` 导出依赖约束，并使用策略固定摘要的私有 uv，避免旧安装器的浮动下载。
恢复时沿用同一计划。普通发布只选择上一正式版；例如候选 v1.9.5 默认仅验收 v1.9.4 → v1.9.5。周期回归的窗口包含目标版，随版本发布推进；v1.9.0、v1.8.2 不再是默认基线。旧布局专项仍可显式点名，约束与私有工具只在该场景准备。
每周一 03:23（香港时间）的 `windows-compatibility.yml` 使用最新已发布包做完整生命周期和滚动窗口内升级，
复用既有制品，无需编译 GUI。该任务在工作流合入默认分支后生效，结果和日志作为 Actions 证据保留 90 天。
手动验收可传入唯一 `dispatch_id`，按运行标题关联 run 并核对 `head_sha`，避免误用其他任务的结果。
最近一次周期兼容任务未通过时，新发布最多扩大到当前滚动窗口及完整生命周期，不恢复已经退出窗口的固定旧版本。手动 `scope=recent-upgrade` 仅验收上一正式版真实升级并检查回执复用，报告不会将跳过的生命周期记作通过。

进度测试必须显式提供 `PDF2ZH_TEST_CONTROL`、`PDF2ZH_TEST_UV`、`PDF2ZH_TEST_PYTHON` 和
`PDF2ZH_TEST_VERSION`；缺失或程序版本不符即失败。Slint 专项工具必须传 `--version`。

本地验证尚未升版的重构时，可为 `test_windows_upgrade.ps1` 显式传入
`-AllowSameVersion`，使用已发布 wheel 升级到内容不同的候选 wheel；降级和相同 wheel
仍会被拒绝。此类本地记录不替代正式发布的冻结计划与制品回执。
历史数据夹具使用旧版实际模块写入，再由候选读取任务、术语包、翻译记忆、模型缓存、
划词与词典、恢复上下文和质量状态；合成账户、已有输出与诊断备份另做内容校验。
原生安装向导测试可用 `PDF2ZH_TEST_INSTALLER` 指定单文件 EXE，覆盖自解压和控制中心交接。
窗口与按钮按实际就绪状态等待；安装完成记录落盘不等于界面已完成切换。
完整生命周期在回滚和迁移后验证任务路径及数据夹具，并检查安装预检不会读取继承的数据目录。
需要单独复验目录迁移时，可运行 `test_windows_relocation_data.ps1 -Root <隔离安装目录> -Package <ZIP> -Wheel <wheel> -Receipt <回执路径>`；
它升级该隔离安装、迁移至新目录、删除源安装后验证数据和历次备份，最后归档证据并清理进程。

本机测试失败时先区分产品故障与环境问题。产品故障不能通过切换平台、删断言或
改为标准验证来绕过；环境问题可以交给远端验证，但“未运行”不能记为“通过”。

## 时间、复用与恢复

入口打印 `.local-dev/reports/<run>/release-state.json`；恢复使用
`bash scripts/release.sh <version> --resume <state.json>`，并保持原选项。
记录固定产品提交、dispatch 标识、准确 run ID/attempt；成功阶段先核验再复用。
构建后验证失败时，恢复只复用已证明构建成功的包；没有构建证据时停止，不隐式重编译。
观察超时不会被记作远端失败，下载同时限制总时长和无进展时长。

标准验证成功后，在历史扩展和归档之前保存 `standard-validation.json`；远端 schema 1 记录原 run/attempt，
本地 schema 2 记录独立执行 ID、Windows/Python/Rust 环境、各阶段与所有选中升级场景。两者均记录
冻结计划、生命周期范围及八项制品的大小和 SHA-256。只有每个标准步骤与回执生成步骤均
成功，才允许恢复时复用；同时核对原 run/attempt、完整计划、当前制品摘要和未变化的验收代码。
同一提交不同构建的内容不能混用，改变基线、脚本或策略后也不能沿用旧回执。
`--resume` 在标准回执已成功保存并上传时自动请求复用；最终仍由工作流核对回执和
实际制品，通过后才跳过标准步骤。只有构建成功而没有验证回执时，复用包并执行所选检查。

每个升级场景在归档前写入独立回执，再保存到 `local-validation.json.cases/`；汇总结果保存在托管报告 `validation.json` 及发布记录旁的 `local-validation.json`。恢复逐项核对计划、源提交、验收脚本、前后 ZIP/wheel 摘要，仅复用完全匹配的通过场景；失败或运行中的汇总不能作为整体验收通过。
它只需证明计划中未在标准阶段执行的历史升级；完整生命周期由远端标准回执证明。
发布门槛同时核对标准回执、计划、必需本机场景与最终 ZIP/wheel 摘要。
活动发布记录带 `.keep`，不会被普通报告清理。
构建的八项产品制品及 `checksums.json` 外，另保存绑定计划的 `validation-plan.json`；
`standard-validation.json` 也随验证制品保存，五项公开 Release 附件保持不变。
旧 schema 或缺少标准回执的构建需要复用原包重新验证，不能直接续发。

手动 `publish-pypi.yml` 始终要求 `build_run_id`（远端构建或本地产物接收任务），包括只发布 PyPI 的情况；它复用
成功验证 run 的原包，校验上述契约，不提供临时重打包后直接发布的分支。

普通续发只补缺失附件；同名同内容复用，冲突则停止并要求显式同版本替换。
`--no-pypi` 只跳过上传，公开 wheel/sdist 仍必须齐全且与最终制品匹配。

- 快速 Windows 检查目标为几分钟内完成，10 分钟为硬上限。远端发布构建当前上限
  为 90 分钟；新增耗时项目应说明覆盖的具体风险，优先加入本机或按需扩展入口。
- 本机复用工具链、release 编译及下载缓存。远端使用现有 Rust/LLVM/Skia/uv 缓存；
  缓存命中不能替代验证，缓存告警也不自动判定产品失败。
- Rust 依赖缓存只在成功任务结束后写入，避免构建前失败留下不完整缓存并长期精确命中。
  验收脚本单独修复时可复用已生成的制品；记录制品源提交与验收脚本提交，不重编译。
- 同一提交、同一制品已成功的检查直接复用。观察连接中断或下载失败时先查看既有
  run，不立即重新构建；制品变化后不能复用旧哈希对应的结果。
- 网络等暂时故障可有限重试失败阶段。重复失败后保留日志并定位原因，不无限重跑
  整套发布，也不为取得绿灯删掉必要检查。
- 安装测试只操作隔离目录、端口、注册表与快捷方式。结束或失败后停止测试进程，
  保留可排查的记录；不得关闭正式服务或遗留重复控制中心窗口。
- 架构变更后的验收失败应先集中核对旧假设，再执行受影响测试。启动标记不等于
  启动脚本已结束；停止或升级前需等交接完成。清理必须覆盖隔离路径内的控制中心、
  Python 和 PowerShell 工作进程，并复核进程身份，不能只按进程名批量结束。
- 制品复用也须能从干净 checkout 开始；每组测试自行准备临时目录和报告目录，
  不依赖被跳过的编译步骤或此前执行过其他测试。

## 发布环境与 PyPI 等待

Windows 发布入口及 Actions 使用 `python scripts/windows_powershell.py <script.ps1> ...`。
它定位系统 Windows PowerShell 5.1，只在子进程环境移除 `PSModulePath`，先检查模块、CIM、版本与命令来源。
这覆盖 PowerShell 7 经 Git Bash/Python 启动 5.1 的继承问题；不写系统设置，不依赖个人安装路径。
原始验收错误、清理错误分别保留，收尾计算摘要使用 .NET，防止再次因命令自动加载丢失失败回执。

本地与 `publish-pypi.yml` 共用 `scripts/pypi_publication.py`，以已验证清单中的 wheel/sdist 为准。
同时核对版本 JSON 的文件大小/摘要与安装器使用的 Simple 索引。默认总等待 600 秒，单次请求最多 10 秒，
间隔按 5/10/20/30 秒增加；总预算包含请求和间隔。404、缺文件、429、5xx 和暂时连接失败可有限重试，
内容冲突、撤回文件、认证及证书错误立即停止。每次输出缺少的文件、HTTP/缓存状态及已等待时间。
`PDF2ZH_PYPI_WAIT_SECONDS` 或 workflow 的 `visibility_timeout` 可配置 0–1800 秒，0 为单次探测。

上传、公开核验、GitHub 发布分为独立 job。仅上传 job 获得 OIDC 权限；后续步骤复用同一 run 的已验证清单。
公开核验失败时，恢复重跑原 run 的失败 job，成功的上传不重复执行；派发结果未知时先观察原 run。
公开核验通过前不分发 Windows 安装器。等待超时保留 pending 回执，不能记为发布成功。

Actions 制品 ZIP 按不可变 artifact ID 缓存在 `.tmp/cache/release-artifacts/`，复用先核对摘要，
解包后仍执行版本、提交、完整验证契约及八项制品检查。目录清理只归档证据，遍历时直接排除依赖目录；
归档和删除持续显示进度。删除失败记录 `cleanupStatus=pending` 并保留工作目录，不覆盖验收原始结论。
新计划使用 schema 3；策略或验收代码变化后，旧计划/回执保留原证据，新验收须生成新计划，不静默改写旧回执。
